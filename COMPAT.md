## Scope limits

This is a bounded inventory of representative object instances, not proof of full documented-public-API parity. Special methods (`__iter__`, `__len__`, and similar) are excluded from the attribute total; XML/OPC plumbing is excluded by design. The signature check does not compare type annotations or return annotations. Signatures unavailable to `inspect.signature` on a runtime are counted separately, not guessed; for example, inherited `int` method `Length.conjugate` is uninspectable on Python 3.9 but exists on both implementations. Neither inventory checks behavior for every documented method, input, or object state. The remaining engineering target is a complete official-API member/signature/behavior matrix.

## How this is checked

A name answering is the start, not the end. Focused API behavior is compared with python-docx in `tests/test_compat_parity.py` and `tests/test_authoring_v03.py`; the writer and authoring suites exercise file output, and `tests/test_enums.py` compares all 471 enum members. `examples/docs_recipes.py` runs python-docx's own documented recipes through both libraries and diffs the results.

## Out of scope, on purpose

- `docx.oxml` — the lxml element API. Code that builds `<w:p>` elements by hand
  is not migrated by changing an import; `docviews` reads and writes the same
  XML through its own layer.
- `part`, `element` on document objects, and `docx.shared`'s `ElementProxy`,
  `Parented`, `StoryChild`, `TextAccumulator` — all hand out lxml proxies.
- `doc.part` / package internals (`docx.opc`) — `docviews` exposes `main_part`,
  `parts` and part names instead.
